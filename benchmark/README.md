# Benchmark behind Figure 2

GRASS against 21 other open-source packages (xarray-spatial on NumPy and on dask as two series) in eight raster
operations on an Iceland 10 m DEM of 2.14 billion cells. This folder holds the measured results, the notebook that
turns them into Figure 2 and every number the paper cites, and the scripts that reproduce the whole benchmark from
nothing: the software in pinned versions, the data from its public sources, every timed run, the agreement checks,
the selection of the plotted points and the figure.

- `figure2.ipynb`: the supplement to Figure 2. Method, the figure, the numbers in the paper, every point with its
  package, repeat runs, agreement and versions, all computed from `results/`, `settings.csv` and `versions.csv`.
  It does not run the benchmark and needs only Python with pandas, matplotlib and Jupyter.
- `results/`: what the benchmark measured (below).
- `settings.csv`, `versions.csv`: what was run, with which parameters, and in which versions (below).
- The scripts: `reproduce.sh` and the steps it calls.

## Published results and how each file was derived

| File | Content | Derived by |
|---|---|---|
| `results/runs.tsv` | one row per timed run: start time, run name, resolution, MemoryMax, exit code (0, 124 time limit, 143 memory limit or the package's memory check, wait = machine never quiet), wall time, peak RSS, cgroup peak, load, available memory, CPU time | measured: `run.sh` appends a row after each run of `02_runs.sh`. Published are the runs behind Figure 2 and the paper: the candidate runs listed in `settings.csv` (with their repeats and memory-limit reruns) and the runs that did not finish. Runs of other settings or other stacks made while setting up the benchmark are left out, and so are three runs whose output could not be read (Whitebox Workflows wrote classic TIFF above 4 GiB in its first cost run and its two series runs); their reruns, cost written as SAGA grids and series as BigTIFF (2026-11-26), are in it, and the scripts now write those formats |
| `results/sedona/runs.tsv` | the same for the steps of the Apache Sedona pipelines in Figure 2 (algebra, resampling, series) | measured: `run_sb.sh` |
| `results/machine.csv` | CPU, memory, kernel, governor, turbo, GRASS version and the batch settings at the start of each batch, one row per batch | `02_runs.sh` (`info`) writes a `machine_*.txt` per batch; `machine.py` merges them into this table (without the host name) |
| `results/paper_numbers.csv` | every number the paper's benchmark paragraph and Figure 2's caption cite, each with how it is computed | `paper_data.py` applies the selection rules to the two `runs.tsv` files (`04_figure.sh`); the notebook rebuilds it and checks that it is identical |
| `results/figures/figure-benchmark.png` | Figure 2 | `make_p1.py` from the points `paper_data.py` selects (`04_figure.sh`) |
| `results/agreement/*.txt` | agreement of every output with a reference | `03_checks.sh` on the outputs of the published runs |
| `settings.csv` | tool or function, parameters, memory setting, threads and flags of every run that is a candidate for a point, keyed by its run name in `runs.tsv` (column `run`) | written by hand from the commands in `tools/*.sh`, `ops_*.py` and the `*_flowacc.*` pipelines; the rows are the candidate runs of `paper_data.py` (`ops_ice()`) that are in `runs.tsv`, and the notebook checks that every candidate has a row; `flags` are those of `paper_data.py` |
| `versions.csv` | version of every package, its environment and where the version comes from | generated by `versions.py` from `envs/` (conda explicit lists, pip freezes), `00_envs.sh` (versions it downloads) and `results/machine.csv` |

Measured run records are TSV (written by the shell harness); derived tables and descriptions are CSV.

To redraw Figure 2 and rebuild `paper_numbers.csv` from the run records: `RESULTS=results ./04_figure.sh` (or run the notebook).

## Reproducing the benchmark

```sh
./reproduce.sh            # = ./00_envs.sh && ./01_data.sh && ./02_runs.sh && ./03_checks.sh && ./04_figure.sh
```

Settings are in `config.sh` (cores, threads, memory limit, results directory, repeats, limit levels). Each step can
run on its own; `02_runs.sh` resumes where it stopped.

## What you need

- **Machine:** Linux x86_64 with at least 128 GB of RAM (the runs are capped at 110 GB with `MemoryMax`; the reference
  machine has 125 GB), 8 free cores, about 1.5 TB of free disk (outputs of the last run of each package about 0.6 TB,
  the GRASS project up to 0.2 TB, inputs and tiles about 0.15 TB). Reference: Intel Xeon W-2295 (18 cores, 36
  threads), 125 GB, Ubuntu 24.04.4, kernel 6.8.
- **For stable times:** Intel turbo off (`/sys/devices/system/cpu/intel_pstate/no_turbo` = 1, checked by
  `02_runs.sh`), the `performance` CPU governor, no other work on the machine. Every run waits until the machine is
  quiet (1-min load, available memory, no other `r.watershed`) and is pinned to `CPUS` (default 0-7).
- **systemd user scopes with the memory controller (cgroup v2):** `run.sh` starts every run with
  `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0` and reads the scope's `memory.peak`. Run outside any
  container or sandbox that hides host processes or the user's systemd bus. The Sedona harness (`run_sb.sh`) needs no
  systemd.
- **System packages** (Ubuntu 24.04 names): GNU `time`, `util-linux` (`taskset`), `coreutils` (`numfmt`), `curl`,
  `unzip`, `bzip2`, `git`, `python3-venv`, `openjdk-21-jre-headless` (GeoTools, Sedona), `apt` access for
  `apt-get download` (SAGA), and the GRASS build dependencies: `build-essential flex bison make gcc g++
  libgdal-dev libproj-dev proj-bin proj-data libgeos-dev libsqlite3-dev libtiff-dev libpng-dev libcairo2-dev
  libfreetype-dev libfontconfig-dev libfftw3-dev libzstd-dev libbz2-dev libnetcdf-dev libreadline-dev libpq-dev
  libsvm-dev libglu1-mesa-dev libxmu-dev zlib1g-dev python3-dev python3-numpy gettext` (configure options in
  `grass_build_o2.sh`).
- **Network** for `00_envs.sh` and `01_data.sh` (about 30 GB of ArcticDEM tiles).

## Steps

| Step | Script | What it does | Time |
|---|---|---|---|
| 0 | `00_envs.sh` | micromamba 2.9.0 and six conda-forge environments from explicit lists (R + terra, TauDEM, RichDEM, QGIS + GDAL, PCRaster, gdistance), traudem 1.0.3 from CRAN, five Python venvs from pip freezes, SAGA 9.3.1 Ubuntu packages extracted without root, GRASS 8.5.0 built with `-O2`, Orfeo ToolBox 9.1.1, GeoTools and Sedona jars, WhiteboxTools 2.4.0, the Spark environment file | ~1 h |
| 1 | `01_data.sh` | ArcticDEM v4.1 10 m mosaic tiles (24) and Natural Earth 10 m countries; a GRASS project with the patched tiles and the Iceland polygon; `prep_iceland.sh`: landmass bounding box, sea masked, voids filled, 20/50/100 m averages; -9999 no-data; `project_iceland`; least-cost inputs (`prep_cost.py`); the 12-layer r.sun stack (`prep_series_sets.sh`) | ~3 h |
| 2 | `02_runs.sh` | every timed run, one at a time (stages below) | ~5 days |
| 3 | `03_checks.sh` | agreement of the outputs with GRASS or GDAL, flow accumulation sanity check (untimed) | ~3 h |
| 4 | `04_figure.sh` | `paper_data.py` (selection rule) → Figure 2's points and `paper_numbers.csv`; `make_p1.py` → Figure 2 | 1 min |

### Stages of `02_runs.sh`

1. **unlimited:** every package and GRASS configuration once, MemoryMax 110 GB (RichDEM and pysheds in Float64:
   100 GB), operations in the order flow accumulation, least-cost path, relief, resampling, slope, algebra, series,
   focal median. Within an operation GRASS runs first; every other run is capped at k × GRASS's fastest time,
   k = 10 when GRASS takes up to 0.5 h, 3 from 2 h on, log-linear between, at least 1 h (rc 124 in `runs.tsv`).
2. **repeats:** a second run of the five short operations (relief, resampling, slope, algebra, series), tag `_r2`.
3. **rep3:** a third run of every pair of short-operation runs whose times differ by more than 5 %, tag `_r3`. The
   point uses the median of a package's runs.
4. **longrep:** a second run of a sample of long runs (`LONG_SAMPLE` in `config.sh`: the three GRASS flow
   accumulation runs, GRASS least-cost and focal median, GDAL focal median, WhiteboxTools and pyflwdir flow
   accumulation), tag `_r2`. It checks that one run is enough for the long operations; the published points include
   these second runs. About 8 h.
5. **limits:** the same runs under 1 GB and under the DEM size in memory (8.0 GiB). A run is tried when its unlimited
   peak was at most 1.25 × the limit, or when it is a low-memory setting (GDAL with a 64 MB cache, terra `todisk`,
   xarray-spatial on dask, `r.terraflow memory=500`). As in the
   published run, the limit levels cover the packages of the main batch (GRASS, GDAL, terra, SAGA, both Whitebox
   packages, xarray-spatial, TopoToolbox, RichDEM, the flow-accumulation tools); `LIMIT_ALL=1` adds the others.
6. **sedona:** Apache Sedona algebra, series and resampling as pipelines (GDAL tiles, Sedona, GDAL mosaic) on
   `run_sb.sh`, whose memory is the JVM's plus the Python driver's peak RSS and which has no memory limit.

`PLAN=1 ./02_runs.sh` lists the runs without running anything. `STAGES="unlimited"` etc. runs a subset.

## Outputs of a run

| File | Content |
|---|---|
| `$RESULTS/runs.tsv` | one row per run: time, run name, resolution, MemoryMax, exit code (0, 124 time limit, 143 memory limit or the package's memory guard, wait = machine never quiet), wall time, peak RSS, cgroup peak, load, available memory, CPU time |
| `$RESULTS/sedona/runs.tsv` | the same for the Sedona steps |
| `$RESULTS/machine_*.txt` | CPU, memory, kernel, governor, turbo, GRASS version at the start of each `02_runs.sh` (`python3 machine.py $RESULTS > $RESULTS/machine.csv` merges them) |
| `out/figure2/paper_points.csv` | every point of Figure 2 with its package, run, flags, time and memory ratios, the quartiles, the linked lower-memory point, and for runs that did not finish the reason (not published: the notebook lists the points) |
| `$RESULTS/paper_numbers.csv` | the numbers the paper cites, each with how it is computed (copied from `out/figure2/`) |
| `$RESULTS/figures/figure-benchmark.png` | Figure 2 |
| `$RESULTS/agreement/agree_*.txt`, `fa_check_ice10.txt` | agreement (`figure2.ipynb`, Agreement) |

The selection rule is in `paper_data.py` (docstring and `ops_ice()`): per package and operation the candidates are its
repeats, memory-limit reruns and settings that only trade memory; the point is the least-memory candidate within 5 %
of the fastest; a candidate needing at most half of that memory is the linked lower-memory point; the median and
quartiles are over the other packages' points. Flags (approximate, incomplete, no path, user-written) are set there
from the agreement results and the method, not from the times.

## What is not automated, and known differences

- **Agreement checks right after the runs:** `03_checks.sh` reads the outputs of the last run of each package in `out/`
  and exports GRASS's from its mapset, so run it right after `02_runs.sh`, before any other run overwrites them.
  The published `results/agreement/` was made on 2026-11-25 after the seven GRASS operations were run again, untimed
  and with the same settings, because a later test run had overwritten their outputs. Its series check is from
  2026-11-26, after the Whitebox Workflows series rerun, with `.sdat` outputs (SAGA) included.
- **Turbo and governor** are set by the machine's administrator (`echo 1 > …/intel_pstate/no_turbo`,
  `cpupower frequency-set -g performance`); `02_runs.sh` only checks turbo.
- **ArcticDEM download URL:** `01_data.sh` assumes the layout `…/mosaic/v4.1/10m/<tile>/<tile>_10m_v4.1.tar.gz` of the
  Polar Geospatial Center repository; the reference project was built from the same 24 tiles (raster history of
  `r.patch`) with the steps of `01_data.sh`. Check the cell counts it prints: 10 m 49,368 × 43,326, 1,060,309,263 with
  values. Cite: Porter et al. 2023, ArcticDEM Mosaics v4.1, doi:10.7910/DVN/3VDC4W; Natural Earth 10 m admin-0.
- **WhiteboxTools 2.4.0:** the `whitebox` Python package downloads the current binary; `00_envs.sh` prints its
  version. If it is newer than 2.4.0, put the 2.4.0 binary at `.venv/lib/python3.12/site-packages/whitebox/WBT/`.
- **GRASS build dependencies** are system packages (list above); the reference build used Ubuntu 24.04's GDAL 3.8.4
  and PROJ 9.4.0.
- **Download locations** of Orfeo ToolBox 9.1.1, the Maven jars and the CRAN archive of traudem are the public ones at
  the time of the run; if one moves, the version is what matters (`versions.csv`).
- **Not reproduced by the default run:** in the published run, the main batch ran on 2026-10-30/31, the series on the r.sun stack on
  2026-11-10, the limit levels on 2026-11-06/07, the added packages on 2026-11-12/13 and their repeats on 2026-11-16, all on the same machine and
  settings. On 2026-11-26 Whitebox Workflows' series ran again with BigTIFF output, and QGIS relief and slope and the
  Apache Sedona pipelines got their second runs (Sedona resampling a third, its first two differed by 5.7 %). The third runs (`rep3`) were made only for the eight pairs of
  the added packages that differed by more than 5 %; `02_runs.sh` applies the rule to every package.
- **Times will differ** on other hardware; the figure plots ratios to the median of all packages (GRASS included), and the selection rule
  works on any machine. Memory peaks should be close for the same versions.
